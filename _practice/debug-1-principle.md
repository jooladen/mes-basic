## 0. 한 문장 정의

> **배제법**은 **기대 Output을 먼저 못박고**(Output First), 결과가 기대와 다를 때 **범위를 반으로 줄인 뒤 결과 쪽부터 거꾸로** 가면서, 각 지점의 **실제 값이 기대와 맞으면 근거와 함께 지우고**, **처음 어긋나는 곳**을 범인으로 찾는 방법이다.

### 준의 첫 정리 → 보완

| 준의 첫 정리 | 보완 |
|---|---|
| 에러 발생 시 | **기대와 다른 결과가 나왔을 때.** 에러 없이 결과만 틀리는 경우가 더 많다 (02: `RAW`, 03: 0건) |
| 원하는 아웃풋이 아닌 걸 확인 | 그대로 ⭕ — 이게 출발점 |
| 하나씩 뒤져서 | **먼저 줄이고, 그다음 하나씩.** 반으로 자르기 → 거꾸로 추적 → 비교 |
| 범인을 찾는다 | **범인이 아닌 것을 근거와 함께 지운다.** 남은 것을 확인한다 |
| Output First가 대전제 | 그대로 ⭕ + **실제 값 관찰**(브레이크포인트)이 짝으로 필요 |

> 용어 주의: 수학의 "소거법"(연립방정식)과 다르다. 영어로 **Process of Elimination**.

## 1. 🧸 숨바꼭질로 이해하기

친구를 찾아야 해요.

1. **친구는 빨간 옷을 입었다** ← 이걸 먼저 알아야 함 (**Output First**)
2. 옷장을 열었더니 파란 옷 → "**여기 아님**" ✏️ 지움
3. 침대 밑에 아무것도 없음 → "**여기 아님**" ✏️ 지움
4. 커튼 뒤에 빨간 옷이 살짝 보임 → **찾았다!**

- 친구 옷 색을 모르면 → 아무것도 지울 수 없다 (**기대 Output이 없으면 배제법 불가**)
- 옷장을 열어 보지 않고 "아마 없을 거야" → 지우면 안 된다 (**관찰 없이 지우지 않기**)
- "친구는 2층에 올라간 적 없어" → 2층은 통째로 안 찾아도 됨 (**반으로 자르기**)

## 1-2. 🍙 김밥으로 이해하기 — 범위 줄이기 기준은 어떻게 찾나?

> 숨바꼭질이 "**왜** 지우나"라면, 김밥은 "**어디를 기준으로** 자르나"이다.
> rows/columns, 디비/화면 같은 **정해진 기준이 없는 낯선 프로그램**에서도 쓰는 방법.

김밥이 너무 짜요. 어디서 짜졌을까요?

```
밥 짓기 → 밥에 간하기 → 재료 넣기 → 말기 → 썰기 → 🍙 짠 김밥
```

### 방법 ① 단계마다 맛보기 (어디서?)

- 밥 짓고 맛봄 → 안 짬 ✅
- 간한 밥 맛봄 → **짬!** ❌
- 👉 **"밥에 간하기"**에서 짜졌다. 재료, 말기, 썰기는 **볼 필요 없음.**

**범위 줄이기 기준 = "맛볼 수 있는 곳"이다.**
만드는 순서를 적으면, 단계와 단계 **사이마다** 맛볼 곳이 생긴다. 그게 자르는 기준이다.
rows/columns, 디비/화면은 이 "맛볼 곳"에 붙은 **이름**일 뿐이다.

맛볼 곳을 고르는 조건 두 가지:
1. 거기서 **값을 볼 수 있나?** (브레이크포인트, 로그, 쿼리 직접 실행)
2. 거기서 **나와야 할 값을 아나?** (Output First를 그 지점에 적용)

둘 다 ⭕인 곳 중 **가운데쯤**이나 **가장 보기 쉬운 곳**부터 맛본다.

### 방법 ② 엄마 김밥과 비교하기 (무엇이 다른가?)

- 엄마 김밥은 안 짜고, 내 김밥만 짜다.
- 밥도 같고, 김도 같고, 재료도 같다. **다른 건 소금 넣은 양뿐.**
- 👉 같은 것은 전부 무죄. **다른 것 하나**만 본다.

### 방법 ③ 언제부터 짰나? (언제부터?)

- 어제까진 괜찮았는데, **오늘 소금을 새로 샀다.**
- 👉 **새로 바뀐 것**부터 본다.

### 03번에 옮기면

```
키워드 입력 → 전체 품목 꺼내기 → 키워드로 고르기 → 표에 담기 → 🍽️ 0건
```

| 방법 | 03번에서 |
|---|---|
| ① 맛보기 | 꺼낸 품목에 '모듈' 있음 ✅ → 고른 결과 0건 ❌ → **"고르기"에서 틀어짐** |
| ② 비교하기 | 코드(`ITM-0009`)는 찾아지고 이름(`모듈`)은 안 됨 → 같은 길인데 **코드와 이름을 다르게 다루는 곳**만 봄 |
| ③ 언제부터 | "지난주에 키워드 칸을 붙였다" → 그때 바뀐 곳부터 봄 (단, **키워드 칸 자체**인지 **같이 바뀐 다른 곳**인지는 확인 필요) |

### 다른 종류의 프로그램에도 똑같이

| 증상 | 만드는 순서 (← 사이마다 맛볼 곳) |
|---|---|
| 엑셀 다운로드 금액이 이상함 | 엑셀 파일 ← 파일 쓰기 ← 숫자 포맷 변환 ← 합계 계산 ← 조회 결과 ← 조건 |
| 야간 배치 후 재고가 안 맞음 | 재고 테이블 ← UPDATE ← 수량 계산 ← 입출고 집계 ← 대상 추출 ← 기준일자 |

화면이 없어도, 디비가 아니어도 **순서를 적으면 맛볼 곳이 생긴다.**

### 공식 이름

| 김밥 비유 | 공식 이름 | 한 줄 뜻 | 도구 |
|---|---|---|---|
| ① 단계마다 맛보기 | **Wolf Fence 알고리즘** / **이분 탐색 디버깅** (Binary Search Debugging) | 울타리로 반씩 갈라서 늑대가 있는 쪽만 남긴다 | 브레이크포인트, 로그 |
| ① + 결과부터 거꾸로 | **역방향 추적** (Backward Tracing) | 증상 지점에서 원인 쪽으로 거슬러 간다 | 호출 스택, F12 |
| ② 엄마 김밥과 비교 | **델타 디버깅** (Delta Debugging) | 되는 입력과 안 되는 입력의 **차이**에서 원인을 찾는다 | 입력 바꿔 가며 재현 |
| ③ 언제부터 | **회귀 이분 탐색** (Regression Bisection) | 잘 되던 버전과 안 되는 버전 사이를 반씩 자른다 | `git bisect` |
| 전체를 묶는 말 | **결함 위치 찾기** (Fault Localization), **체계적 디버깅** (Systematic Debugging) | — | — |

> 출처 메모: 델타 디버깅은 Andreas Zeller의 *Why Programs Fail*에서 정리됨. Wolf Fence는 1982년 Edward Gauss의 글이 유래로 알려져 있으나 **미확인** — 인용 전에 확인할 것.

### 한 줄 요약

> **어떤 프로그램이든: 만드는 순서를 적고 → 중간중간 맛보고(①), 잘 되는 것과 비교하고(②), 언제부터인지 본다(③).**

## 2. 세 가지가 한 몸으로 움직인다

```
Output First   →  "무엇이 나와야 하나"        (판정 기준)
배제법          →  "그 기준으로 정상인 곳을 지운다"
거꾸로 추적     →  "지우는 순서는 결과 쪽부터"
```

| 원칙 | 없으면 어떻게 되나 |
|---|---|
| Output First | "정상"인지 판정을 못 한다 → 값을 봐도 구경만 하게 됨 |
| 배제법 | 의심 가는 곳을 다 고쳐 보는 "찍기 수정"이 된다 → 다른 곳이 깨짐 |
| 거꾸로 추적 | 입력부터 전부 읽게 된다 → 시간 낭비, 길을 잃음 (O-3 이탈) |

## 3. 배제 도구 4가지 (뒤질 곳을 줄이는 순서)

### 도구 1. 반으로 자르기 — "rows냐 columns냐"

| 판별 질문 | rows (조회) | columns (표시) |
|---|---|---|
| 무엇을 바꾸나 | **몇 줄이 나오나** | **한 칸이 어떻게 보이나** |
| 오라클로 치면 | FROM · WHERE | SELECT 표시 · 그리드 컬럼 설정 |
| 이 프로젝트에서 | 저장소 → 서비스 필터 → `useSearch` → `rows` | `buildColumns` → `render` → `typeLabel` 등 |
| 이런 증상이면 | 건수가 틀림, 0건 | 건수는 맞는데 글자·포맷이 틀림 |

→ 한쪽으로 판정되면 **다른 쪽 파일은 열지 않는다.**

### 도구 2. 결과 쪽부터 거꾸로 — 흙탕물 시냇물

증상이 보이는 지점(화면)에서 출발해 **한 칸씩 위로** 올라가며 물을 떠 본다.
**깨끗한 지점과 더러운 지점 사이**가 범인.

| 다음 칸으로 가는 법 | 오라클 시스템 | 이 프로젝트 |
|---|---|---|
| 호출한 곳 찾기 | 서비스 메서드명 검색 | 함수 이름에서 **F12** |
| 다음 파일 열기 | 쿼리 ID로 XML 검색 | **import 경로** 따라가기 |
| 값 확인 | 로그의 파라미터·바인드 값 | **브레이크포인트 / 로그포인트** |

### 도구 3. 되는 것과 안 되는 것 비교 — 차이만 남기기

같은 길을 지나는 두 입력 중 **하나는 되고 하나는 안 되면**, 두 입력이 **같이 지나는 길은 전부 무죄**.
**둘이 다르게 취급되는 부분**만 남는다.

예: 03번 — 품목코드 `ITM-0009`는 찾아지고, 품목명 `모듈`은 0건
→ 키워드 입력 칸, 서비스, 검사 함수의 비교 로직은 **둘 다 지나감 → 무죄**
→ 남는 것: **코드와 이름을 다르게 취급하는 곳**

### 도구 4. 값 찍기 — 관찰 없이 지우지 않는다

"아마 정상일 거야"로 지우지 않는다. **실제 값을 보고** 지운다.
방법은 `debug-2-breakpoint.md` 참조 (인라인 브레이크포인트, 로그포인트, console.log).

## 4. 사례 적용

### 02번 — 유형 칸이 `RAW`로 나옴

🎯 기대 Output: 유형 칸에 `원자재 / 반제품 / 완제품`

| 용의자 | 근거 | 판정 |
|---|---|---|
| rows 전체 | 유형 필터로 조회하면 **제대로 걸러짐** | ❌ 지움 (도구 1) |
| 코드 목록 (`useCodes`) | 검색 콤보에 **한글이 잘 나옴** | ❌ 지움 (도구 3: 콤보는 되고 표는 안 됨) |
| DataTable 셀 렌더링 | `render`가 있으면 그 결과를 찍음 — 정상 동작 | ❌ 지움 |
| 유형 컬럼의 `render` | `typeLabel`을 부를 뿐 | ❌ 지움 |
| **`typeLabel`** | `find` 결과가 `undefined` → `?? value`로 `RAW` | ⭕ **범인** (도구 4로 확인) |

### 03번 — 품목명으로 검색하면 0건

🎯 기대 Output: `모듈` 입력 → `완제품 모듈 X100 / X200 / X300` **3건** (`items.mock.js`에서 확인)

| 용의자 | 근거 | 판정 |
|---|---|---|
| columns 전체 | **0건** → 그릴 게 없음 | ❌ 지움 (도구 1) |
| 데이터 창고 (`items.mock.js`) | '모듈' 품목이 **있음** | ❌ 지움 |
| 키워드 입력 칸 (관리자 추측) | 브레이크포인트에서 키워드 값이 `모듈`로 들어오는지 → **준이 확인할 것** | ❓ |
| 키워드 검사 함수의 비교 로직 | **품목코드로는 찾아짐** | ❌ 지움 (도구 3) |
| **검사 함수에 넘기는 "볼 칸 목록"** | 남은 용의자 → **준이 확인할 것** | ❓ |

> 오라클이었다면: 테이블에 데이터 있음(배제) → 바인드 값 `:keyword = '모듈'` 정상(배제) → **WHERE 절이 어느 컬럼을 비교하나** 확인.
> 필터가 WHERE에 있든 JS `filter`에 있든 **조회 조건 누락**이라는 결함 유형은 같다.

## 5. 실전 체크리스트 (어떤 화면이든)

1. [ ] **기대 Output을 한 문장으로** 적었다 (건수, 글자, 값까지 구체적으로)
2. [ ] **실제 Output**을 적었다 (기대와 어디가 다른가)
3. [ ] **rows냐 columns냐** 판정하고 근거를 적었다 → 반대쪽은 열지 않는다
4. [ ] 증상이 보이는 지점을 **출발점**으로 정했다 (파일 + 이름)
5. [ ] **되는 입력 / 안 되는 입력**을 찾아 비교했다 (있다면)
6. [ ] 한 칸씩 거꾸로 가며 **실제 값을 찍고**, 기대와 맞으면 근거와 함께 지웠다
7. [ ] **처음 어긋나는 지점**을 범인으로 특정했다 (파일 + 함수/변수 이름)
8. [ ] 남이 말한 추측(관리자 등)도 **같은 방식으로** 확인했다 — 믿지도, 무시하지도 않는다
9. [ ] 고친 뒤 **기대 Output이 나오는지** + **원래 되던 것이 여전히 되는지** 확인했다
10. [ ] 실험용 변경(console.log, 주석 처리 등)을 **되돌렸다** → `git diff`

| 실수 | 왜 위험한가 | 대신 |
|---|---|---|
| 기대 Output 없이 값부터 찍기 | 값을 봐도 맞는지 모름 | 1번 체크부터 |
| "아마 정상" 하고 지우기 | 진짜 범인을 지울 수 있음 | 값을 찍어 보고 지운다 |
| 의심 가는 곳을 바로 고쳐 보기 | 고쳐서 우연히 되면 진짜 원인을 모름, 다른 곳이 깨짐 | 확인 → 특정 → 수정 순서 |
| 이전 문제의 습관대로 같은 곳부터 보기 | 02는 columns, 03은 rows — 방향이 반대 | 매번 도구 1부터 |
| 남의 추측을 그대로 믿기 | "키워드 칸 때문"처럼 미끼일 수 있음 | 추측도 용의자 목록에 넣고 배제 |
| 질문에 코드를 손으로 옮겨 적기 | 한 글자 차이로 엉뚱한 결론 | 파일에서 **복사** |
| 디버깅 흔적을 남긴 채 커밋 | `//?? value` 같은 임시 변경이 새 버그가 됨 | 10번 체크 |
